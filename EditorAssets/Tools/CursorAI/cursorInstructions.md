# ゲームエンジン開発における自律エージェントの行動指針

## 1. 開発の進め方
- タスクは必ず小さな単位（例: 数学ライブラリの実装、レンダラーの初期化など）に分割して実行してください。
- 1つのタスクが完了し、ビルドおよびテストが成功したら、必ずそこで一度停止し、人間にレビューを求めてください。
- ゲームエンジン・エディタ・その他ツール・アプリケーション等の機能を実装／修正／変更する際は、**ゲーム開発での用途**を考慮して仕様を決めてください。用途が推測できないものは実装せず放置し、報告・確認を行います（§6.4）。

## 2. 人間に指示を仰ぐべきタイミング（停止条件）
- 1つのサブタスク（マイルストーン）が完了したとき
- アーキテクチャの根幹（メモリ管理、スレッドモデル、API選定など）に関わる設計判断が必要なとき
- コンパイルエラーやリンクエラーが3回以上連続で解決できないとき（**`/loop` 中は §7.1 に従いループ全体は止めずロールバック後に別タスクへ**）
- 既存のコアシステム（レンダリングループなど）を大幅に破壊する変更が必要なとき

## 3. 報告のフォーマット
タスク完了時または中断時は、必ず **`EditorAssets/Tools/CursorAI/progress_report.md`** を更新する。進捗報告の正本はこのファイル **のみ**（`progress_report` 類似名の別ファイルは新規作成しない）。

**蓄積（上書き禁止）:** 既存本文は削除しない。ファイル末尾に `---` の区切り線を入れ、新しい **`## セッション yyyy-mm-dd HH:MM`**（日本時間）ブロックを **追記**する。各ブロックに以下 1〜5 を記載する。最上部の「最新サマリー」1 行だけは任意で更新してよい。ループ停止後も **1 ファイルで全セッションを通読**できるようにする（分割・ローテーションはユーザー指示時のみ）。

**報告ファイル一覧（いずれも蓄積・上書き禁止）:** 現状は **`progress_report.md` のみ**（正本。`progress_report` 類似名の別ファイルは作らない）。

1. 現在の進捗状況と完了したこと
2. 発生した課題または設計上の選択肢（メリット・デメリット）
3. 次に実行すべきステップの提案（人間からの指示待ち状態にする）
4. **`## 実装済みと判断した項目（コード確認・即時 [x]）`** … §6.2 で roadmap を `[x]` にしたもの。**実装コミットが無いセッションでも必須**。0件なら「なし」と1行。
5. **`## 保留・着手見送り（§6.3）`** … 今回の手入れ・選定で **着手しない** と判断した項目と **依存で巻き添え見送り**した項目。**理由必須**。0件なら「なし」と1行。
6. **`## 用途不明で確認待ち（§6.4）`** … ゲーム開発での用途が推測できず放置した項目と、ユーザーへの確認内容。0件なら「なし」と1行。
7. **`## 推測した用途（§6.4）`** … 今回実装／修正／変更した機能ごとに、推測したゲーム開発での用途と、それを踏まえて決めた仕様を箇条書きで記載。実装が無いセッションは「なし」と1行。

## 4. 完了の定義（このリポジトリ）

- **ビルド:** `EditorAssets/Tools/CursorAI/buildDevelopment.cmd`（`Project/CG2_BuildUp.vcxproj`、Configuration=Development、Platform=x64）
- **テスト:** 自動テストは未整備。ランタイム確認が必要な変更は `progress_report.md` に「未実施／実施済み」を明記する。
- **サブタスクの粒度:** 原則 1 ビルド単位・少数ファイル。新 API やレンダパス全体の差し替えは分割する。

## 5. Git とチェック

- **通常:** **コミット**は人間が明示したときのみ（例:「コミットして」「タスク完了でコミット可」）。
- **例外（`/loop` 稼働中・§7.1）:** tick ごとにビルド成功したサブタスクは **`loopMergeTickToDevelop.ps1`**（`-NextBranchName` 必須）でコミット → develop マージ → develop push → **当該作業ブランチのローカル／リモート削除** → **次タスク用ブランチを develop から作成** まで **追加確認なし** でよい。
- **develop 統合（§8）:** コミット許可後も §7.1 と同じライフサイクル（**1 タスク＝1 作業ブランチ**）。統合後に作業ブランチを残さない。
- **統合前に止める／確認する例外（リスクが読めるとき）:** merge コンフリクト、force push（とくに master）、シークレット混入の疑い、master へのマージ、次ブランチ名が backlog／命名規則から決められないとき（§8）。
- husky pre-commit で cspell が走る。未知語は `exclusion.dic` など既存の仕組みで解消する（シークレットをコミットしない）。
- **master にはマージ・force push しない**（develop が統合先）。

## 6. タスクの取り出し順

1. `task_backlog.md` の未完了（上から）
2. 着手前に **`EditorAssets/Tools/CursorAI/docs/feature-memos/roadmap_rough.md`** を確認する。`[]`（大）/ `〇` / `・` の下書きがあれば **§6.0 で `roadmap.md` に起こしてから**、**§6.1 で構造を手入れ**する（`spec:` 行があればその md も）。
3. `task_backlog` で行を指定されていなければ、手入れ後の **`- [ ]` のみ**を上から1件選ぶ（**`- [x]` は完了、`- [-]` は保留としてスキップ**。§6.3）。
4. サブタスク完了時は **該当行を `- [x]` に更新**（`roadmap.md` および `task_backlog.md`）。
5. それでも不明なら会話文脈と `progress_report.md` から 1 件を提案し、**承認を得てから**着手する。

### 6.5 タスクごとの作業ブランチ（必須）

**原則:** 長期間使い回す単一の作業ブランチ（例: 汎用 `feature/SemiAutoDevelopFlow`）で複数タスクを続けない。

**1 タスクの定義**

- **roadmap 使用時:** `- [ ]` の **小見出し 1 行** ＝ 1 タスク（1 ビルド単位のサブタスクでも、この行が完了単位ならその行に対応する）。
- **`task_backlog.md` 使用時:** 未完了行 1 件 ＝ 1 タスク。

**着手前（毎回）**

1. 今回のタスクの文言から **`branchNaming.md`** でブランチ名を決める（`feature/` / `fix/` / `chore/`）。
2. **`startTaskBranchFromDevelop.ps1 -BranchName "feature/…"`** を実行する（`develop` を pull したうえで新規ブランチ作成・push）。
3. `progress_report.md` に **着手ブランチ名** と **対応する roadmap 行** を 1 行書く。

**完了後（ビルド成功・§4）**

- **通常:** `finishTaskGit.ps1`（§8）。
- **`/loop`:** `loopMergeTickToDevelop.ps1 -CommitMessage "…" -NextBranchName "feature/…"` … マージ後は **完了したブランチを削除** し、**次タスク用に既に `-NextBranchName` を切っている** 状態で次 tick／次タスクへ進む。

**次ブランチ名**

- 次の `- [ ]` から先に名前を決め、マージスクリプトの `-NextBranchName` に渡す。次タスクが未決なら **ユーザーに確認してから** マージする。

### 6.0 `roadmap_rough.md` からの起こし

**取り込み対象の判定**

- 「（以下に貼る）」以降に `[...]`（大見出し・**1行が `[`～`]` のみ**）/ `〇` / `・` の行が **1行も無い** ときは §6.0 を **スキップ**（テンプレのみ）。
- 正本テンプレ: `EditorAssets/Tools/CursorAI/docs/feature-memos/roadmap_rough.template.md`

**下書きの記法（本文なし・箇条書きのみ）**

| 記号 | 大中小 | `roadmap.md` |
|------|--------|----------------|
| `[テキスト]` | 大見出し（`<>` 不可・プレビュー崩れ防止） | `## テキスト` |
| `〇テキスト` | 中見出し | `### テキスト` |
| `・テキスト` | 小見出し | `- [ ] テキスト` または **実装済みなら `- [x]`**（§6.2） |

上記3種以外の行は取り込み対象にしない。

**起こし手順**（貼付ありのとき）

1. 文言を解釈し、曖昧なら **§6.1 の曖昧さ手続き**に従い、明確になるまで起こしを保留してよい。
2. 内容を **`roadmap.md` にマージ**する（`##` / `###` / `- [ ]` または `- [x]`。既存の `[x]` は維持。重複は統合）。各 `・` について **§6.2** で即時チェックの可否を判定する。
3. `progress_report.md` に起こした項目と、**即時 `[x]` にした項目**（根拠を1行ずつ）を列挙する。
4. **退避とテンプレ再生成**（取り込み成功直後、順番固定）:
   - `roadmap_rough.md` の **1行目** に `取り込み済み yyyy-mm-dd(ddd)_HH-MM-SS`（日本時間）を挿入する。
   - その `roadmap_rough.md` を **`roadmap_rough_old.md` に改名**する（既存の `roadmap_rough_old.md` は **上書き**してよい）。
   - `roadmap_rough.template.md` の内容で **新しい `roadmap_rough.md` を生成**する。
5. 起こしだけでマイルストーンとする場合はここで停止してよい（ユーザーが「起こしまで」等と言った場合）。停止時も 4 の退避は行う。

### 6.1 roadmap の解釈と構造の手入れ（実装前に毎回）

大見出し（`##`）・中見出し（`###`）・小見出し（`- [ ]`）も、**いきなり実装しない**。コードベースと roadmap を突き合わせて解釈し、必要なら `roadmap.md` を更新する。**実装単位は小見出し（`- [ ]`）のみ**（`###` のみの行は §6.1 で `・` 相当の子を足す）。

| 判断 | 行動 |
|------|------|
| 抜けている | サブ項目を **追加**（1ビルド単位） |
| 大きすぎる・複数関心が混在 | **細分化**（子の `- [ ]` に分割。親は集約用の見出しまたは1行説明のままでもよい） |
| 重複・同義・粒度がバラバラ | **統合**（1行にまとめ、完了済み `[x]` は維持。統合元は削除し意味を失わないよう文言を残す） |
| 解釈できた | `progress_report.md` に解釈の1行要約と、今回着手する1件を書く |
| **既に実装が万全**（§6.2） | 小見出しを **`- [x]`** に更新。実装作業は行わない |
| **着手保留**（§6.3） | **`- [-]`** に更新。実装しない。依存項目も同様に見送り |
| **用途が推測できない**（§6.4） | **`- [ ]` のまま** 放置。ユーザーに確認し、`progress_report.md` に追記 |

**手続き**

1. 対象セクション（見出し＋配下のチェック）を読み、既存実装を軽く確認する。**§6.2** により実装済みの `- [ ]` はその場で `- [x]` にしてよい。
2. roadmap を更新した場合は `progress_report.md` に **変更理由**（追加／細分化／統合／即時完了）を列挙する。
3. **実装は `- [ ]` の1件のみ**（`- [~]` 可）。**`- [x]` / `- [-]` は飛ばす**。親セクション全体を一括実装しない。
4. アーキテクチャ根幹に触れる細分化・統合は §2 どおり停止する。

**曖昧さの扱い（推測で実装しない）**

1. **解釈が難しい** … ユーザーに **具体的な質問**（2〜5個、選択肢付きが望ましい）をチャットで投げ、`progress_report.md` にも同じ質問を書き、**回答まで実装を開始しない**。
2. **質問後も曖昧** … 要件の **再定義** をユーザーに要請する（roadmap の該当行をどう書き直すかの提案を添える）。**実装は行わない**。
3. ユーザーが「roadmap の手入れまで承認して」と言った場合は、構造更新後に **実装前に一度停止**する。

### 6.2 実装済みと判断して即時 `- [x]`（起こし・手入れ時）

小見出し（`- [ ]` / 下書きの `・`）について、コードベースを確認し **要件を満たしていると合理的に判断できる** ときは、起こし・マージの時点で **`- [x]`** とする。以降の半自律では **実装工程をスキップ**する。

**即時チェックしてよい目安**

- 該当機能の呼び出し・UI・データパスが既に存在し、下書きの趣旨と **明らかに一致**する
- 直近の `Development | x64` ビルドが成功している（起こし直後で未ビルドのときは、コード上の根拠が十分なら可。不確かなら `[ ]` のまま）

**即時チェックしない**

- 挙動未確認で推測のみ、一部だけ実装、TODO／スタブ、下書きが曖昧
- 判断に迷う → `[ ]` のまま。必要ならユーザーに1行確認

**`progress_report.md` への必須報告**（即時 `[x]` ごとに **必ず** 追記。§3 の項目4）

- 形式（表推奨）: `| roadmap の文言 | 根拠（パス・シーン・API） | 判定（万全／一部要確認） |`
- 起こしのみ・手入れのみ・実装スキップのみのマイルストーンでも **更新してから** 停止する
- チャットでも同内容を短く触れてよいが、**正本は progress_report.md**

### 6.3 保留・依存ブロック（着手見送り）

**今すぐ実装すると無駄な悪影響が出る**と合理的に推測できるタスク、および **そのタスクの完了（または方針決定）が前提**になっている項目は、**実装に手を付けず放置**する。他の `- [ ]` だけに取り組む。

**見送りの例**

- 前提アセット／シリアライズが未整備なのに上位機能（プレハブ運用、Lua バインド大量追加など）を先にやると捨てやすい
- 設計未確定のままコア API を変えると既存シーン・エディタが壊れるリスクが高い
- ロードマップ上「実装対象外」（例: メンタル・運用メモ）をコードタスクと誤認した場合

**手続き**

1. 手入れ・タスク選定時に保留候補を洗い出し、該当行を **`- [-]`** にする（文言はそのまま）。解除はユーザー指示または前提完了後。
2. **依存見送り**: 保留タスクを前提とする `- [ ]` も **`- [-]`** にし、理由に「依存: ○○」と書く。前提が外れていれば単独で着手してよいものは `- [ ]` のまま。
3. **`progress_report.md` §3 項目5** に必ず記載（表推奨）: `| roadmap の文言 | 種別（悪影響／依存） | 理由 | 再開条件 |`
4. 保留があっても **他の着手可能な `- [ ]` があれば実装を続行**できる。全部保留なら停止してユーザーへ。

### 6.4 ゲーム開発用途の考慮（実装・修正・変更の前に毎回）

機能の実装・修正・変更では、**ゲーム開発のどの場面で使われるか**を推測し、仕様・API・UI・既定値をその用途に合わせる。

**用途の例**

- ランタイム（ゲームプレイ中の処理。フレーム毎のコスト・メモリ確保に注意）
- 制作（エディタでのレベル／アセット編集。制作者の繰り返し作業を減らす）
- デバッグ・プロファイリング（開発ビルド限定で良いか）
- ビルド・配布（出荷ビルドへの影響、アセットパイプライン）

**用途が推測できないとき**

1. 実装に手を付けず **一旦放置** する（roadmap の行は `- [ ]` のまま。§6.3 の保留 `[-]` とは区別する）。
2. ユーザーに **用途の候補を選択肢付きで** 確認する。
3. roadmap 使用時は **`progress_report.md` §3 項目6** に必ず追記する（表推奨）: `| roadmap の文言（または機能名） | 推測できなかった点 | 用途の候補 | ユーザーへの質問 |`
4. 他に着手可能な `- [ ]` があれば実装を続行してよい。全部が確認待ち・保留なら停止してユーザーへ。
5. 回答を得たら、用途を `roadmap.md` の該当行の補足（または `spec:` の md）に1行残してから着手する。

**実装・修正・変更後の報告**

機能を実装／修正／変更したら、**`progress_report.md` §3 項目7** に推測した用途を **箇条書き** で追記する。機能ごとに以下を書く。

```markdown
## 推測した用途（§6.4）

- **機能名（roadmap の文言）**
  - 用途: 例）レベルデザイナーがエディタ上で配置オブジェクトを一括調整する
  - 使用場面: ランタイム／制作（エディタ）／デバッグ／ビルド・配布 のいずれか（複数可）
  - 用途から決めた仕様: 例）エディタ専用ビルドのみに含め、ランタイムのフレームコストに影響させない
```

- ユーザーから回答を得た用途は「推測」ではなく **「確認済み」** と明記する。

### 6.6 用途別・実装ギャップスキャン（キーワード・`/loop`）

**起動キーワード（1 回 = 1 tick）:** **`ギャップスキャンを実行して`**

チャットで上記を送る、または `/loop` の gap-scan tick が同文言を送る。

**正本（ギャップ在庫）**

| ファイル | 役割 |
|----------|------|
| `EditorAssets/Tools/CursorAI/docs/implementation_gaps.md` | 人間が読む一覧（用途別不足） |
| `EditorAssets/Tools/CursorAI/docs/implementation_gaps_index.json` | ID・`scopeKey`・重複禁止の機械正本 |
| `EditorAssets/Tools/CursorAI/docs/use_case_scenarios.md` | UseCase ごとの「できるべきこと」シナリオ |

**tick 計画（優先順位・範囲はスクリプトが 1 件だけ選定）**

| ファイル | 役割 |
|----------|------|
| `planGapScanTick.py` | 未スキャン優先・UseCase ローテーションで **シナリオ 1 件** を選び `gap_scan_tick.json` へ出力 |
| `gap_scan_tick.json` | 当該 tick の範囲（`scanId`・`scenarioId`・`areaHint`・`searchHints`） |
| `gap_scan_state.json` | ローテーション・シナリオスキャン回数 |
| `recordGapScanTick.py` | tick 完了記録（`scans` 追記・ローテーション進行） |
| `syncImplementationGapsMd.py` | index から `implementation_gaps.md` の一覧・履歴を再同期 |

`progress_report.md` はセッション報告のみ（ギャップ本文を正本にしない）。

**1 tick の手順（キーワード受信後は毎回この順）**

1. `python3 EditorAssets/Tools/CursorAI/planGapScanTick.py` を実行し **`gap_scan_tick.json` を Read**（`status: in_progress` の計画に厳守。自前で範囲を広げない）。
2. `implementation_gaps_index.json` を Read。
3. 計画の `scenarioId` / `scenarioText` / `areaHint` / `searchHints` のみを対象に、**「その用途でできないこと」** をコード・仕様（`spec` md）と突合。
4. 各候補に `scopeKey` = `primaryUseCase | Area | PrimarySymbol | Kind | Anchor` を付与。`scopeToId` にあれば **同一 ID を更新**（新規 ID 禁止）。
5. 新規のみ `GAP-<Area>-<Subject>-<NNN>` を採番（`nextSequence` を index で管理可）。`summary` は `【Play|Authoring|Debug|Ship】…` 型を守る。
6. **用途が推測できない** 候補は GAP 化せず、`pendings` に `PENDING-UC-*` のみ。
7. `syncImplementationGapsMd.py` を実行。
8. `recordGapScanTick.py --new-ids … --updated-ids …` を実行。
9. `progress_report.md` に **`scanId`・`primaryUseCase`・`newIds` 件数** を追記。

**コード変更**

- ギャップスキャン **のみ** の tick では **ビルド不要**・**§6.5 作業ブランチ不要**（ドキュメント／index のみ）。コミットはユーザー許可または `/loop` 方針に従う。
- ギャップ解消の実装 tick は従来どおり §4 ビルド・§6.5 ブランチ運用に従う。

## 7. モードの開始・終了

- **開始:** ユーザーが「半自律」「半自律稼働」等と明示したとき。
- **終了:** 「半自律終了」「通常モード」等。`progress_report.md` に終了を1行追記してよい。

### 7.1 `/loop` 稼働（報告の蓄積と自動停止）

- **ループ中も §3 と同じく追記のみ。** tick ごとに新セクションを足す。過去セクションの削除・差し替えはしない。
- **ループ起動:** 生の `while { sleep }` ではなく **`EditorAssets/Tools/CursorAI/loopRoadmapDev.ps1`** を使う（サイズ監視付き）。間隔は `-IntervalMinutes`（既定 90）。
- **各 tick の先頭で必須:** `loopReportGuard.ps1` を実行。exit code `2` なら **ループを止め**、`-AppendStopNoticeIfOversize` で `progress_report.md` 末尾に停止理由を追記してから終了（手動の `while` ループが残っている場合は該当 PowerShell プロセスも停止）。
- **上限:** `progress_report.md` のファイルサイズが **200kB（204800 バイト）を超えたらループを自動停止**。末尾に「ループ自動停止」セクションを追記し、理由に **自動記述ファイルの肥大化** を書く（文言は `loopReportGuard.ps1` のテンプレに合わせる）。
- **手動停止:** ユーザーが「ループ停止」と言ったときは tick 用シェルを終了し、任意で `progress_report.md` に手動停止を 1 行追記してよい。

#### 7.1.0 tick／タスク着手前

1. roadmap から今回の **小見出し 1 件**（`- [ ]`）を選ぶ（§6.5）。
2. **`startTaskBranchFromDevelop.ps1 -BranchName "…"`** で **develop から** 作業ブランチを切る（既にそのブランチ上で未コミット作業が無いこと）。

#### 7.1.1 ビルド成功時（tick 1 件完了）

1. `buildDevelopment.cmd` 成功
2. `roadmap.md` の該当行を `[x]`、`progress_report.md` に **§3 形式のセクション追記**
3. 次の `- [ ]` から **`NextBranchName`** を決める（`branchNaming.md`）
4. **`loopMergeTickToDevelop.ps1 -CommitMessage "…" -NextBranchName "feature/…"`** … develop マージ・push → **完了ブランチ削除** → **次ブランチ作成**（§5 例外）
5. `loopRecordLastGood.ps1` は `loopMergeTickToDevelop.ps1` 内で呼ばれる

#### 7.1.2 ビルド失敗時（同一サブタスク）

1. MSBuild ログから **error 行**を抽出（**`パス(行): error` 形式のファイル名・行番号が必須**。無い場合はビルドログ全文の先頭 40 行を貼る）
2. **`loopRegisterBuildFailure.ps1 -RoadmapTask "…" -ErrorLines @('…')`**
3. **1〜2 回目:** 同一タスクの修正を続行（カウンタのみ増加）
4. **3 回目（exit 3）:** **`loopRollbackToLastGood.ps1`** 相当のロールバック後、**`progress_report.md` に「ビルド 3 回失敗でタスク中断」セクション**（スクリプトが追記。推測原因にログ抜粋必須）
5. **別タスクへ:** 失敗タスクに依存しない roadmap の `- [ ]` を選び直す（§6.3 の `[-]` はスキップ）。中断した行は `[ ]` のまま

#### 7.1.3 状態ファイル

- **`loop_state.json`** … `lastGoodCommit`（ロールバック先）、連続失敗回数。エージェントが直接編集せず上記スクリプト経由で更新する。

#### 7.1.4 `/loop` ギャップスキャン（roadmap ループと独立）

- **起動:** `EditorAssets/Tools/CursorAI/loopGapScanDev.ps1`（`progress_report` 200kB 監視は `loopReportGuard.ps1` と同様）。
- **間隔:** `-IntervalMinutes`（既定 90）。各周期のプロンプトは **「ギャップスキャンを実行して」** を含む（§6.6 参照）。
- **1 tick:** `planGapScanTick.py` → スキャン → `syncImplementationGapsMd.py` → `recordGapScanTick.py`。**ビルドしない**。**`loopMergeTickToDevelop.ps1` 不要**（Git マージなし tick でよい）。
- **停止:** ユーザー「ループ停止」、`progress_report` 肥大化（§7.1）、または `use_case_scenarios.md` の全シナリオが十分回った後の手動停止。
- **蓄積:** 正本は `implementation_gaps_index.json` / `implementation_gaps.md`。`progress_report` には scan 要約のみ追記。

## 8. タスク完了時の Git 自動フロー（コミット許可後）

ユーザーが **コミット・プッシュを許可**（例:「コミットして」「プッシュOK」「タスク完了でコミット可」）したとき、半自律モードでは次を **この順で** 実行する。

**§6.5 と同じく、タスク開始時は必ず `startTaskBranchFromDevelop.ps1` で develop から切ったブランチ上で作業すること。**

### 前提

- 変更はステージ済み、ビルド成功、`progress_report.md` 更新済み。
- **当該タスク専用の** 作業ブランチ上にいる（`develop` / `master` 上では実行しない）。

### 手順

1. **次ブランチ名を決定** — `task_backlog.md` の次タスク + `branchNaming.md`。不明なら提案してユーザーに1行確認してから続行。
2. **スクリプト実行**（リポジトリルートから）:
   ```powershell
   powershell -NoProfile -ExecutionPolicy Bypass -File EditorAssets/Tools/CursorAI/finishTaskGit.ps1 `
     -CommitMessage "ここにメッセージ" `
     -NextBranchName "feature/ExampleTopic"
   ```
   既にコミット済みのときは `-NoCommit` を付ける。
3. スクリプトが行うこと: 現在ブランチへ commit（任意）→ push → `develop` を pull → 作業ブランチを **merge** → `develop` を push → ローカル・リモートの作業ブランチ削除 → `NextBranchName` を作成して push。
4. `task_backlog.md` で完了タスクに `[x]`、`progress_report.md` にブランチ名・マージ結果を記載し、**次サブタスク**に入る前に停止（従来どおりレビュー可）。

### 中断・エスカレーション

- **merge コンフリクト** → マージを中止し（`git merge --abort`）、`progress_report.md` に報告。自動解決しない。
- **3回連続**で Git/ビルドが失敗 → 停止条件 §2 どおり人間へ。
- ユーザーが **コミットのみ** と指定した場合は、§8 は実行せず §5 のみ。
